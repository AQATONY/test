# Анализ требований ЭТрН

## Scope

Проверяется функциональность электронной транспортной накладной по процессу из BPMN:

- создание ЭТрН грузоотправителем;
- заполнение первого титула;
- сохранение черновика;
- подписание и отправка титула;
- маршрутизация через оператора ЭДО;
- работа перевозчика с полученным титулом;
- замечания при погрузке;
- выдача QR-кода водителю;
- прибытие водителя на погрузку и разгрузку;
- работа грузополучателя;
- замечания при выгрузке;
- финальная смена статуса на принятие груза грузополучателем.

## Восстановленная модель ролей

| Роль | Основная ответственность | Критичные проверки |
|---|---|---|
| Грузоотправитель | Создает ЭТрН, заполняет первый титул, подписывает, отправляет, получает дальнейшие титулы | Черновик, обязательные поля, права на подписание, статусы после отправки |
| Оператор ЭДО | Доставляет сообщения между участниками | Доставка, дубли, недоступность, ошибки маршрутизации |
| Перевозчик | Получает первый титул, подтверждает, фиксирует замечания при погрузке, подписывает дальнейшие титулы, передает QR-код | Связь с исходной ЭТрН, корректность замечаний, подпись, отправка грузополучателю |
| Водитель | Получает QR-код, прибывает на погрузку/разгрузку, сообщает о прибытии | Валидность QR-кода, привязка к ЭТрН, недоступность/истечение QR |
| Грузополучатель | Принимает груз или отказывается, фиксирует замечания при выгрузке, подписывает титул | Прием/отказ, замечания, финальный статус |

## Состояния, которые должны быть явно описаны

Минимальная статусная модель по BPMN:

| Статус | Кто переводит | Условие перехода |
|---|---|---|
| Черновик | Грузоотправитель | ЭТрН создана и сохранена без отправки |
| Завершен для первого титула | Грузоотправитель/система | Первый титул подписан и отправлен |
| Ожидает отгрузки со склада | Система | Первый титул доставлен перевозчику, перевозчик начал обработку |
| Груз принят к перевозке | Перевозчик/система | Перевозчик подтвердил прием и отправил следующий титул |
| Ожидание транспортного средства на месте разгрузки | Водитель/грузополучатель | Водитель прибыл на разгрузку, грузополучатель должен принять решение |
| Груз принят грузополучателем | Грузополучатель/система | Грузополучатель подписал титул приема без отказа |
| Отказ от груза | Грузополучатель | Грузополучатель отказался принимать груз |

## Requirement gaps

| ID | Риск | Почему важно | Рекомендация |
|---|---|---|---|
| REQ-01 | Конфликт дат 01.09.2026 и 01.09.2024 | Непонятно, какую нормативную версию считать целевой | Уточнить legal target и XSD version |
| REQ-02 | Не описана точная статусная модель | Риск неправильных переходов и отображения статуса разным ролям | Зафиксировать state machine: статус, событие, роль, allowed actions |
| REQ-03 | Не описаны права ролей | Пользователь может подписать чужой титул или увидеть чужие реквизиты | Матрица ролей и permissions |
| REQ-04 | Нет требований к ошибкам ЭДО/ГИС ЭПД | Внешняя интеграция может быть недоступна, а пользователь увидит неверный успех | Описать retry, timeout, dead-letter, ручной повтор |
| REQ-05 | Нет требований к дубликатам сообщений | ЭДО может доставить одно событие повторно | Нужна идемпотентность по УИД/ID файла/номеру титула |
| REQ-06 | Не описаны ошибки электронной подписи | Подпись делает документ юридически значимым | Проверить сертификат, владельца, срок, отзыв, роль подписанта |
| REQ-07 | Нет требований к QR-коду водителя | QR-код участвует в реальном физическом процессе | Нужны срок действия, привязка к ЭТрН, повторная генерация, запрет чужого QR |
| REQ-08 | Не описаны empty/loading/error states | Пользователь может повторно отправить титул или потерять данные | Нужны состояния загрузки, блокировка кнопок, recovery |
| REQ-09 | Не описан аудит изменений | В спорном процессе важно понимать, кто и когда изменил титул | Нужен audit log по статусам, подписаниям, отправкам и ошибкам |
| REQ-10 | Нет миграционных требований | XSD меняются версиями, старые документы должны читаться | Описать backward compatibility и отображение старых форматов |

## Acceptance criteria, которые я бы добавил

1. ЭТрН нельзя отправить без обязательных полей первого титула по XSD.
2. Пользователь видит понятную ошибку, если XML не проходит XSD-валидацию.
3. После отправки титула пользователь не может изменить юридически значимые поля без сценария исправления.
4. Каждый переход статуса происходит только после подтвержденного события от корректной роли или интеграции.
5. Повторная доставка одного и того же сообщения от ЭДО не создает дубль титула и не ломает статус.
6. Ошибка подписи не переводит документ в отправленное состояние.
7. При недоступности ЭДО/ГИС ЭПД пользователь видит статус "не отправлено/ожидает повтора", а не успешное завершение.
8. Замечания при погрузке/выгрузке обязательны, если пользователь активировал соответствующий чекбокс.
9. Отказ от груза завершает отдельную ветку процесса и не должен отображаться как успешное принятие.
10. Все действия с титулами логируются с ролью, временем, результатом и ID внешнего сообщения.
